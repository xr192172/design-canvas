## 1. 缘起与背景

讨论起点是「一个健康的开发 / 数据流该怎么走」的直觉式发问，随后一路推演。中间参考了 **DataFlow-Harness**（北大 OpenDCAI，arXiv:2607.16617）：

- 它让 agent 不是自由生成脚本，而是对**平台原生 DAG（Backend）**做类型化增量变更；
- agent 靠 **Skills（markdown 程序性知识）+ MCP（实时算子注册表 + 流水线状态）**工作；
- agent 通过 **schema / 接口名匹配**来连接，而非人工画线；
- WebUI 是「对话式 + 可视化编辑」双接口，语义层编辑与拓扑层展示分离。

我们的共同之处：`server_registry`（36+ 工具）、`get_dsl`/`edit_dsl`（权威 DSL 资产）、`wizard_steps`/`narrate`（程序性知识 + 人话翻译）与 DSL 协作工作台，一一对应。**最大启示：前端应是「构建面」而非「报表面」，且 agent 按接口名匹配而非画线。**

## 2. 功能 = 一个转换单元

一个功能**原子**定义为：

```
处理(op) + 产物（出度）     ←  入度（吃什么）由胶水层接线提供，功能本体不写死来源
```

- 功能节点在**视图/语义层只声明 做什么(op) + 产什么（出度）**；**入度不绑定在功能上**。
- **入度（来源接线）归胶水层**：项目迁移时功能零改动，只换胶水层的接线/数据池配置（见 5ter）。
- 契约层用数据名注册表校验胶水接的每个入度名字合法（名唯一 / 有出才有入）。

> 说明：最早版本曾把功能定义为“入度 + 处理 + 出度”，后经用户修订为“入度脱离功能、下沉胶水层”。本节为修订后口径。

---

## 3. 核心主张：免连线的声明式数据流

用户明确表达的心智模型：

1. **图中不画「功能 → 功能」的交叉连线。**
2. 功能只需声明「**做什么 + 产出什么（出度）**」；**来源（入度）不写在功能里**，由胶水层接线提供。
3. 依赖靠**数据名匹配**隐式自动接上，来源是运行时（胶水装配）的事。
4. 用户最多想知道「这功能有哪几个前置步骤」，**不想关心数据从 A 还是 B 来**。
5. 想深究才「**埋点**」看明细（例如：功能C ← 甲取自A · 乙取自B）。

好处：
- **加功能不用改线**——新增功能只声明做/产与出度，不回头改任何已有连线。
- **迁移零改动**——入度归胶水层，换项目只换胶水接线，功能本体不动（见 5ter）。
- **底图永远干净**——视图不被线和图淹没。
- 代价：依赖关系要沉在「埋点/展开」里，debug 多一步。

这与 DataFlow agent 按 schema/接口名匹配连接一致。

## 4. 数据池 / 隐式采集（提权）

当某功能需要**多来源数据**时，最初设想是「中间数据池层」，后经用户修正：

- **数据池 ≠ 常驻中间层**，而是一个**「被提权出来的数据产物」**。
- **数据采集 ≠ 图中节点**，而是一个**不显示在图中的隐式功能**（虚线幽灵）。
- 采集把多来源汇聚成一份数据，这份数据**提权成一个图里的数据点（数据池）**，一条线指向目标功能/区域。
- 用户接受度：只要能「声明能做到什么 + 来源」，来源是否画出不重要。

> 后续可落成 DSL 语义：`dataPool` 类型节点 + 入边标记 `implicit:collect`。未落地。
>
> 修正（见 5bis）：数据池随后**被判定退化为普通节点**（出度被多处引用/需汇聚多入度的比例问题），**不再需要 `dataPool` 特殊类型**。本节保留早期设想供追溯。

## 5. 拒绝「端口解析器」，拥抱「数据名注册表 + 两条规则」

我原先提出需要一个「端口解析器（Port Resolver）」来处理同名歧义 / 悬空引用 / 结构不符。**用户否定了这个重量级方案**，给出更省的替代：

> 只需要收集每一个入度 + 项目外入度，维护一张**全局「数据名注册表」**；哪里少了就把字典里该名取掉；重名就不允许取同一个名。

**规则一：② 产出名唯一**
- 重名拒绝登记；同名即同一份数据。
- 根除「同名歧义」；顺带因「一名一定义」而消除「同名不同结构」。

**规则二：① 有出才有入**
- 入度引用的名字**必须已在注册表中**（有对应产出，或为 external 原始入度），否则在**定义期报警**。
- 根除「悬空引用」。

**外部入口**
- 项目外数据 = **原始入度（external）**，预置进注册表。
- 每个功能：`outputs[]`（登记入表）、`inputs[]`（必须命中表）。

**增量维护**
- 新功能声明出度 → 登记名字入表。
- 某名不再被产出 → 移出表，关联入度随之失效（「哪里少了取掉」）。
- 重名 → 拒绝登记。

**运行时**：只是按表把「吃 X」指到「产出 X」——**一次表查，不是解析**。

| 我担心的坑 | 规则 | 结果 |
|---|---|---|
| 悬空引用 | ① 有出才有入 | 定义期根除 |
| 同名歧义 | ② 产出名唯一 | 定义期根除 |
| 结构不符 | 被 ② 顺带消掉 | 不需要单独检查 |

## 6. 人机交互：语义层编辑 vs 拓扑层装配

- **人**：在「语义层」编辑——功能卡片上「吃什么 / 产出什么」的标签（改的是**节点属性/元数据**，**不碰连线**）。
- **机器**：在「拓扑层」把语义**装配**成隐式实线，用户不看。
- **闭环**：看到卡片 → 手动或让 AI 改某个输入口的来源 → 更新契约 → 图 / DSL 刷新。
- 结论：**只要声明 + 可编辑来源 + 讨论，就达成健康的人机交互。**
- 缺的不是「声明」或「交互」，是**把声明翻译成可运行拓扑的那座桥**——即第 5 节的「注册表 + 两条规则」校验。

## 7. 与现有 DSL/契约的关系（预留方向，未落地）

- `workbench_data.ts` **契约 v1 保持冻结、稳定**（前端窗口正在对接）。

  - 新增 `dataPool` 节点 +执 `implicit:collect` 边。
  - 层折叠边：边可指向 `layer`（把整层当一个可折叠单元）。
  - 校验/并发作为**两端元数据**（`edges[].attr { validate, concurrency }`），折叠，debug 才展开；**不进连接图**（职责分离：图只画数据流）。

---

### 补充 5bis：入度/出度是「开放的集合」，不设限种类

入度、出度各自都是**开放集合**，任意多种，**不是「原始/增量」二选一**；每种数据名独立在注册表登记。由此带来一个免费简化：

- **数据池退化为普通节点**——只是“出度被多处引用 / 需汇聚多入度”的比例问题，**不再需要 `dataPool` 特殊类型**；是否叫数据池取决于被引用度，与种类无关。模型更干净。

---

### 补充 5ter：胶水层的定位 —— 视图不可见 · 文件可替换

胶水层**不在思维导图/DSL 语义层单独出现**（图上功能天然免连线、吃谁不可见），但**在实现层是一个独立文件**（接线 + 数据池配置）。跨项目时整体扔掉这层胶水、换新胶水，功能本体零改动。即：

- 视图/语义层：胶水透明，不单独成节点或边。
- 实现/文件层：胶水 = 可一次性替换的接线段。

## 8. 决策记录（已定）

- 数据流 **免连线·声明式**（不画功能间交叉线）。
- **否掉**「端口解析器」方案。
- 采用**全局数据名注册表 + ②产出名唯一 + ①有出才有入 + external 原始入度 + 增量维护**。
- 校验/并发等横切关注点**不进图**，只在两端落地（职责分离）。
- 契约 v1 **不因本讨论变更**；本模型作为 v2 预留。
