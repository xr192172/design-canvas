# 思维导图产线化（Production-Line Mind Map）— 愿景与实施依据

> 日期：2026-08-20
> 来源：本窗口讨论（用户提出"功能=产线，工序=小图+解说"的组织结构设想）
> 用途：沉淀思维导图组织结构改造的设计决策；排在 cross-project-brick-harvest 计划之后实施
> 前置：teach 视图分镜（steps）与社区盒已落地；盒内流转排序（拓扑 1→N 青色编号）已落地

---

## 一、动机（用户原始设想）

以探针为例：文件 → 插桩 → 采集数据 → 传输 → 解析 → 入库 → 查询。每个功能是一条**产线**，
每道工序是一段小图+解说；小产线可组成大产线。对软件工程理解，这种"按数据流向组织"
可能比"按代码聚类组织"更贴合心智模型。

## 二、与现状的关系（关键洞察：已埋一半）

当前 teach 视图结构（derive_mind_map.ts）：

```
根 → 功能 → ① 工作步骤（LLM 分镜：1→N 步讲"怎么跑"，每步带 involves 文件清单）
             ② 社区盒（聚类讲"住哪里"）→ 文件卡片（盒内按流转边拓扑排序）
```

**分镜本身就是产线叙事**——但它只是平铺的"旁白"，不是组织骨架；文件卡片仍按社区聚类住。
本改造的本质：**把分镜从旁白升级为骨架**（工序变容器盒，涉及文件住进去，工序间画连线）。

本质差异：
- 社区聚类 = 名词性组织（按"是什么"聚类）→ 回答"系统由什么组成"
- 产线 = 动词性组织（按"先后/数据流向"分段）→ 回答"系统怎么运转"

## 三、关键决策（讨论定论，勿翻案）

### 3.1 分流混合，不全面产线化
- **管线型功能**（数据有明显流向：探针事件流、编译器、请求处理链）→ 产线视图：
  工序盒 + 文件入住 + 工序间连线（带 pill 标签）
- **服务型/辐射型功能**（配置管理、UI、CRUD）→ 保持社区容器视图（无"上道输出喂下道"语义，强套歪曲）
- 判定：LLM 提议 + 人确认（沿用 placeProposals 协同模式），标注 origin=llm
- 小产线 → 大产线：对应 sub_dsl 嵌套（已验证支持渲染浏览）

### 3.2 事实纪律（两条红线）
1. **产线划分不靠 LLM 猜了就定**：LLM 只出候选切分，人确认后才成为设计事实。
   未来校准器 = camera 探针（"工序1的返回值确实是工序2的入参"是运行时可验证事实，
   比静态推断硬）。与积木折叠的"异常才深挖"互为镜像：插桩数据是产线视图的校准器。
2. **共享文件进"公用工位"**：被多工序使用的文件（utils 等）不塞进任何单一工序盒，
   复用现有 shared/foundations 区。

### 3.3 文件归属冲突的呈现
一个文件可能参与多个工序。默认方案：文件住"主要参与"的工序盒（involves 首次/最高频），
其余工序只画连线引用。备选（实现时定）：teach 视图内加 组成/运转 双视图 toggle。

## 四、实施路线图

### Phase 1：分镜骨架化（最小改造，先见效）
- steps 从平铺叙事升级为容器盒：每步一个盒子，involves 文件卡片入住
- 工序间连线：沿用盒内流转样式（青色编号徽章 1→N + pill 标签）
- 判定信号：先不做自动判定，LLM 分镜生成时顺带输出 `pipeline_like: boolean` 提议，
  teach 页面顶部让人确认（确认前保持现视图）
- 验收：探针功能（go-camera 事件流）人肉验证——产线视图是否比社区视图更好懂

### Phase 2：判定自动化 + camera 校准
- 确定性判定信号研究（call 图最长路径/汇点分布等）
- camera 运行时数据流校准产线划分（探针观测函数输入输出）

### Phase 3：大产线嵌套
- 工序盒内嵌套 sub 产线（sub_dsl），小产线组成大产线

## 五、验收标准
- Phase 1 完成时：用户在探针功能上确认产线视图的讲解效果优于社区视图（人肉效果验收）
- 共享文件不重复入住；无悬空连线
