# 活文档 + 变更原因捕获方案 — design-canvas 开发文档

> 日期：2026-08-11
> 来源：本窗口多轮讨论（函数级仿真 → 活文档愿景 → 变更原因捕获 → Agent 开发模式）
> 用途：沉淀"让 Agent 开发时源头记录变更原因"的设计方案，作为后续开发依据
> 前置：本方案复用函数级仿真链路（Go trace 采集 + derive_reasoning），详见 `docs/plans/` 与 `go-lab/agent-shell/cmd/context-trace/`

---

## 一、背景与愿景

### 1.1 活文档愿景（早期提出）
用户早期有过一期设想：design-canvas 应成为**活文档**——能记录**所有变更以及变更原因**，随开发持续演进，而不是一份会变旧的死文档。

### 1.2 关键认知转变：Agent 开发模式
本项目是一个 **MCP**，未来主要由 **Agent** 进行开发。由此产生一个关键洞察：

> **"变更原因"应由 Agent 在设计文档时源头写入，而非事后由 LLM 推断。**

- 传统思路（事后推断）：改完代码 → diff + trace → LLM 复盘"为什么改"。缺点：有**事后合理化（post-hoc）**风险，且多一步。
- 本方案（源头记录）：Agent 开发时**本来就在生成/修改设计文档**，那就在写入设计的同时把原因写进去。原因是设计的**副产物**，不是事后补的。

设计文档本身就是 Agent 与开发人员的**交互界面**，因此记录天然嵌入工作流，无需额外维护。

## 二、现状盘点（基建已就位 90%）

`dsl.annotations[]` 已存在，且配套完整工具链（`src/dsl/annotation.ts` + `src/tools/annotation_tools.ts`）：

| 能力 | 字段/工具 | 状态 |
|------|-----------|------|
| 标注挂到节点/边 | `target_id` / `node_id` | ✅ |
| 标注谁写的 | `author: 'human' \| 'llm'` | ✅ |
| LLM 主动写标注 | `addAnnotationByTool` | ✅ |
| 列表/按节点过滤 | `listAnnotations` | ✅ |
| 标记解决+说明 | `resolveAnnotation`（`resolution_note`） | ✅ |
| 审批流（审计） | `approval_status` + `approval_history` | ✅ |

这些字段说明：**「谁在什么时候、因为什么、改了什么、影响谁、审批状态」** 已经能存下来。活文档的"记录"层已经能工作。

## 三、缺口：缺"原因"的结构化方言

当前 `Annotation.text` 是自由文本，`type` 只分 `comment/question/issue/suggestion/approval`。**描述"这次变更为什么发生"没有一个明确的语义槽位**，导致：
- Agent 写得随意、不可聚合、不可检索
- 无法区分"变更原因"与"一般评论/提问"

### 3.1 最小改动：给 Annotation 增加结构化字段

```typescript
// 拟新增字段（在 src/dsl/annotation.ts 的 Annotation 接口上）
kind: 'change' | 'fix' | 'refactor' | 'feature' | 'perf' | 'other';  // 变更类型
reason: string;   // 自然语言原因（必填，经校验）
evidence?: Array<{ type: 'trace' | 'diff' | 'node' | 'edge' | 'metric'; ref: string }>;
                  // 证据链：绑定可回溯证据，解决信任度问题
```

把 `reason`（原因）+ `evidence`（证据链：trace 节点 / diff 文件 / 数字指标）绑定，**结论与证据同存、可回溯**。

## 四、核心设计：防"LLM 偷懒"的四层校验

### 4.1 直面前提：LLM 会偷懒，不装
LLM 被优化为"用最省成本达成目标"，空格、占位符、套话（"更新代码""修复问题"）对 LLM 是**零成本**。任何把希望寄托在"某个 LLM 自律"的设计都脆弱。**不该问"LLM 会不会自律"，而应设计成"不自律会亏"。**

### 4.2 四层校验链（不靠道德，靠"质量校验 + 证据"）

校验挂在 `edit_dsl`（或 `addAnnotationByTool`）的写入门上，让偷懒本身成为负收益：

| 层 | 规则 | 拦截目标 |
|----|------|----------|
| **L1 非空** | trim 后低于阈值字数 → 拒绝 | 空原因 |
| **L2 信息量** | 命中套话黑名单（"更新代码""修复bug""优化"等无信息量词）→ 拒绝 | 占位符/套话 |
| **L3 实体绑定** | 必须包含 ≥1 个具体实体（trace 节点 / diff 文件名 / 数字指标） | 泛泛而谈 |
| **L4 证据回溯** | 声称的 evidence 必须能查到（trace 节点 token 是否真超限、diff 文件是否存在）→ 对不上打回 | **编造的理由** |

**L4 是最硬的一道**：它把"编原因"的成本抬到比"说实话"还高——LLM 想编一个好理由，得先真去查证据才能编得像。当"编"比"如实"更费劲时，自律自然形成。

### 4.3 落地位置
- 校验做成**独立可测试模块**（如 `src/tools/reason_validator.ts`）
- 在 `edit_dsl` 写入门强制调用，校验不通过则拒绝写入并返回具体原因
- 配套测试用例：空格 / 编造理由 / 真实理由，验证三类输入分别被拦截 / 拦截 / 放行

---

## 五、开发顺序建议

本方案是"活文档"愿景的落地起点，与已进行的函数级仿真共用同一套地基（trace 采集 = 活性文档的"证据"层，derive 生成器 = "原因叙事"层）。

**建议分三步走：**

1. **第一步（最小闭环）**：给 `edit_dsl` 加 `reason` 校验链（L1-L4），跑通"Agent 改设计 → 自动留变更原因 → 可检索"
2. **第二步（结构化）**：扩展 `Annotation` 字段（`kind`/`reason`/`evidence`），迁移现有 annotations
3. **第三步（可读化）**：用 dynamic-style 可读呈现变更历史，支持按子系统/按时间下钻

---

## 六、注意事项与边界

- **强依赖工具层强制**，而非"靠 Agent 自觉"——`edit_dsl` 必须带 reason 参数，否则拒绝写入
- **证据需可回溯**：reason 与 evidence 绑定，防止"拍脑袋编理由"
- **不追求全量解析**：活文档按需/按子系统渐进，避免大图糊、不可读（与星图分层下钻原则一致）
- **活文档要随代码生命周期维护**：靠 hook 在变更时自动触发更新，而非人手补
