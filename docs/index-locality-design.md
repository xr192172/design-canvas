# 拼图式局部索引（按需及时建立）设计

> 2026-09-14 ｜ 用户想法（原话）：
> 「如果能**预计算**一遍，把它划分成**一块块拼图**，命中哪一块拼图就索引哪一块，这样修复会更快。
> 我的意思是——**不用预建立，而是及时建立**：从用户/模型**选中的这个文件**为起点，向周围拓展，
> 直到**撞上这段时间已建立的索引**，然后**连通在一起**。当然这只是技术思想，不一定要这么做。」
>
> 本文用实测数据回答"值不值得"，并给出机制、纪律与落地顺序。

## 1. 结论先行：**成立，收益 85–94%**（实测，非估算）

测量方法（`scripts/probe-dc-locality.mjs`）：把 `design-canvas/src`（296 文件）复制到临时目录 →
建好索引 → **只读地**用索引图算"以某文件为种子、沿 import+call 边扩展 N 跳"的闭包规模，
再按实测冷启成本折算（**41.1ms/文件**）。

| 种子（选中文件） | 出 1 跳 | 出 2 跳 | 入 1 跳 | **双向 2 跳** | 折算耗时 | 相对全量 |
|---|---|---|---|---|---|---|
| `version_upgrade/toolchain.ts` | 3 | 9 | 2 | **17** | **692ms** | 省 **94%** |
| `tools/brickify_cli.ts` | 18 | 31 | 1 | **35** | **1426ms** | 省 **88%** |
| `api/contract.ts` | 1 | 1 | 2 | **43** | **1670ms** | 省 **85%** |
| `tools/function_annotation.ts` | 4 | 8 | 4 | **122** | 4643ms | 省 62% |

⇒ **以选中文件为种子、双向 2 跳 = 0.7–4.6s**，而全量 12.1s。对"打开一个文件就开始问"这类任务，
这就是"零前置"该有的延迟量级。

## 2. 为什么现在做成本很低：三块料都现成

| 需要的东西 | 现状 |
|---|---|
| **"已建好的拼图"是什么** | **就是 `files` 表**（每个已索引文件的 path/mtime/hash）——它天然是"覆盖记录"，无需新造 |
| **缝合（撞上就不重复解析）** | `syncFile` **本来就是增量的**：mtime/size 未变 → `skipped`（零成本）；内容同 → `skipped` |
| **沿边向周围拓展** | 已有 `expandClosure` / `project_root`（import 边 + 别名 + 邻域 importer + 跨语言兜底）——今天用于"改名安全边界"，语义与"拼图扩展"完全同构 |
| **图数据** | 索引里已有 `edges(kind='import'/'call'/'type_ref')` ⇒ 扩展不需要重新解析文件来"找邻居"（已索引文件从图里查，新文件才解析） |

⇒ **缺的只是一个函数**：`ensureIndexAround(db, root, seeds, opts)`。

## 3. 机制：种子驱动的 BFS + 缝合 + 预算

```
ensureIndexAround(db, root, seeds, { depth = 2, maxFiles = 200, directions = 'both' })
  1. 队列 ← seeds（相对路径）
  2. 取出 f：
       ├─ 已在 files 表 → **缝合点**：图里查它的邻居继续扩，不重新解析
       └─ 不在          → 计数 newFiles++，syncFile(f)（增量、单文件原子）
  3. 邻居来源：已索引 → 查 edges；未索引 → 该文件解析后自然产生边（syncFile 内已有）
  4. newFiles 达预算或队列空 → 停；返回
     { newFiles, stitched, closureSize, state: 'ready'|'partial' }
```

**触发点（按工具分档）**：

| 工具类型 | 种子从哪来 | 是否可局部 |
|---|---|---|
| 读/导航（`explore_code read`、`get_dsl` query=node、`read_project_docs`） | **args 里的 file/symbol** | ✅ 可局部（**必须带覆盖度**） |
| 语义搜索（`explore_code search`） | 关键词 → 无精确种子 | ⚠️ 先小批冷启（如 200 文件）+ 后台续建；或按路径/包名粗筛 |
| **编辑/重构**（`edit_code`/`rename_*`/`find_references`/`impact_analysis`） | 目标符号 | ❌ **不可局部** —— 见 §4 |

## 4. ★ 纪律：局部索引服务"读"，不服务"改"

这是本方案唯一不能让步的地方，理由是**失败模式不对称**：

- 读少了 → 答案是"没见过"，**诚实地不完整**（可接受，只要标注）；
- 改漏了 → **静默改错**（引用没跟着改、importer 没重定向）——这正是本项目 `find_references`
  现在遇到"无索引"时**直接拒绝**而不是给半份答案的原因。

因此：

1. **只读路径**：可以用局部索引，但返回必须带 **`coverage: { indexedFiles, closureSize, partial }`**，
   并在 `partial=true` 时明说"我只索引了 N 个文件，可能漏 X 方向"（对齐"不静默撒谎"纪律）。
2. **编辑路径**：必须先把闭包**扩到闭合**（沿 importer 方向直到没有新文件），再动手；
   扩不动（超预算/超时）就**明确拒绝并报原因**，绝不"带着不完整索引改代码"。
   —— 这就是把今天的"扩到闭合"语义，从"安全边界"复用到"索引边界"。
3. **本质上需要全量的查询**：`code_health`（孤儿文件/未用导出）、跨包 `impact_analysis`、
   "全仓搜某字符串"——必须能**识别出这类查询**并触发全量/后台，否则答案会**错**（不是"不完整"而是"错"）。

## 5. 与"后台续建"的关系：互补，不冲突

用户上一轮提的"后台续建"和这一轮的"拼图"是同一件事的两半：

| | 前台（本轮） | 后台（上轮） |
|---|---|---|
| 时机 | 首次调用，**按需** | 空闲时 |
| 范围 | 种子闭包（几十个文件） | 剩余全部 |
| 目标 | 把首调用从 12s 压到 **0.7–4.6s** | 让"全局类查询"在不远的将来可用 |
| 交会点 | **缝合**：后台补的块与前台建的块在 `files` 表处自然连通，**不重复解析** | |

⇒ 建议的顺序：**先做前台拼图（收益立现）→ 再加后台续建（补齐全局能力）**。
（现在的实现是"首调用全量阻塞 12s"，两边都没做。）

## 6. 风险与边界（诚实清单）

1. **答案完整性**：局部索引下"漏引用"的观感风险 ⇒ 靠 §4 的覆盖度标注 + 编辑路径扩到闭合来兜。
2. **拼图边界 vs 跨包波及**：`impact_analysis` 依赖跨包边；局部化会截断 ⇒ 该工具走"扩到闭合"档。
3. **失效语义**：局部索引下，**未索引文件被改动**时不会被保鲜（它本来就不在 `files` 里）；
   一旦扩展触达它，`syncFile` 会按当时内容建——语义正确，无需额外机制。
4. **不要预计算分块**：用户自己也修正了（"不用预建立，而是及时建立"）。
   预计算分块会引入"分块表"这一新真相源（漂移风险），而 **BFS + 缝合不需要任何预计算**。
5. **并发**：多个 agent 同时扩展同一区域 ⇒ 复用今天的"单写多读"纪律（写前取锁/拿不到就等）。

## 8. 增量更新逻辑（回答"看门狗触发更新后，AST 这部分怎么算"）

### 8.1 结论：**不是重算全仓，也不只是"重算引用"；分四档，各司其职**

| 档 | 触发 | 做什么 | 代价 |
|---|---|---|---|
| **① mtime/size** | 文件被碰过 | `files.modified_at/size` 比对；**没变就直接跳过（连读内容都不读）** | ≈0 |
| **② content_hash** | 碰过但可能没真改（git checkout / 编辑器 touch） | 读内容算 hash；与 `files.content_hash` **相同 ⇒ skipped，不解析 AST** | 读文件 |
| **③ 真变了 → 重解析这个文件** | 内容 hash 不同 | `parseFileFull(file)`（AST）→ 重写**该文件自己的** nodes/edges/imports/未决引用；同时用 `symbolSpanHash` 逐符号算 span 归一化 hash，产出 `symbol_diffs`（added/removed/changed），并用 `norm_hash`（剔注释+去空白）区分"符号外变更" | 17.8ms/文件 + DB |
| **④ 跨文件引用解析** | 上一步产生了**未决引用**（`unresolved_refs` 里同文件内没命中的 call/type_ref） | `resolveCrossFileCalls()` **只查索引里已有的符号表**（`SELECT name, file_path FROM nodes`）+ 本文件的 import 边定位目标文件 → 写 `edges(kind='call', metadata.cross=true)`。**不重解析任何其它文件** | 纯 DB |

⇒ **你的直觉对了一半**：确实"不需要重算全仓"，而且**跨文件引用解析确实不重解析对方**（只查符号表）。
但**AST 的重算粒度是"文件"而不是"引用"**：一个文件内容变了，它的整棵 AST 会重新解析一遍
（`parseFileFull` 是文件级 API）；引用只是解析产物之一。也就是说：

- **改 A 文件** ⇒ 重解析 A（AST）→ A 的边/未决项重写 → ④ 把 A 的跨文件引用解析到 B/C…（B/C 不动）；
- **改 B 文件的注释/格式** ⇒ ② 或 `norm_hash` 判为"符号外变更" ⇒ 可以不重写符号表（避免无谓波及）。

### 8.2 ★ 修正（2026-09-14 实测）：不会有"悬空边"，真问题是**引用方的边被删后不会重建**

原先的判断是"手工改名会产生悬空边（误报）"——**实测证伪**：

- `edges` 对 `nodes` 有 `FOREIGN KEY … ON DELETE CASCADE`，且连接一直开 `PRAGMA foreign_keys = ON` ⇒
  B 的旧符号节点被删时，**A 指向它的边会被数据库自动删掉** ⇒ 索引里**不会留悬空边**。
- 但由此产生的是**另一个更隐蔽的问题**：A 没变、不会被重解析 ⇒ 它的边**被删掉后不会重建**
  ⇒ `find_references` / `impact_analysis` 在 A 这个方向上**静默漏一条引用**（漏报）。

**修法（已实现）**：刷新时，把"指向本轮变更/删除符号名"的**已解析引用重新打开**
（`unresolved_refs.status = 'resolved' → 'pending'`，纯 SQL，不解析文件），交给随后的
`resolveCrossFileCalls` 重解析 —— 连得上就连到新符号，连不上就**明确标 `failed`**（而不是静默消失）。
另外：`added` 的符号名也一并带上，这样"符号改名又改回来 / 搬到别的文件"时，
之前标 `failed` 的引用有机会重连（`reopenRefsTo` 用"名字现在是否还在索引里"决定要不要重试，
避免"每轮空转重试"）。实测：改名 → 1 条引用重开 + 明确 failed；改回来 → 重新连上。

**这才是"只重算引用部分"的完整版**：不只是重算"被改文件的引用"，还包括"**指向它的文件**"。

> 顺带一条工程教训：这次修法一开始被 `try/catch` 吞成了"静默 0 条"（node:sqlite 的命名参数键
> 不能是纯数字，`{1: nm}` 抛 `Unknown named parameter '1'`）。**被吞的异常必须能被测试看见** ——
> 现在测试直接断言 `refsReopened ≥ 1`。

## 9. 「双向摊开」怎么支持：不是 AST 不支持，而是**入边的信息不在这个文件里**

> 用户问（2026-09-14）：「本来想通过一个文件的**引用方向**和**被引用方向**，像一张网一样往四面摊开，
> 但后面又想到 **AST 解析可能不支持**这种事情 —— 想支持的话该从什么方向入手？」

### 9.1 先纠正归因

- **AST 完全支持"引用方向"**：文件里写了 `import ... from './x'` / `x.foo()` ⇒ 解析它就得到
  **向外的边**（`import`/`call`/`type_ref`），也就是今天索引里已有的边。
- **"被引用方向"不是 AST 的能力问题，而是信息分布问题**：`谁 import 了我` 的信息
  **不在我这个文件里**，它散落在**别人的文件**里。所以只有两条路：
  (a) 把别人也解析一遍（= 全量索引，才有全局反向边）；(b) **去磁盘/文本层反查**。
- 我们实测到的"S1 入边只能看见已索引的引用方"，就是这个事实的直接后果 —— **不是 AST 的锅**。

### 9.2 ★ 关键实测：反向边**不必付 AST 的价**（296 文件项目）

| 做法 | 成本 | 相对 AST | 说明 |
|---|---|---|---|
| ① **AST 全解析**（基线） | **7726ms**（26.1ms/文件） | 100% | 今天的冷启动主成本 |
| ② **文本级 import 反查**（正则，**不需要 AST**） | **6ms**（0.02ms/文件） | **0.1%** | 命中 1275 条 import |
| ③ **轻量提及扫描**（正则落"文件→提及名"） | **47ms**（0.16ms/文件） | **0.6%** | 25 万次提及 → 1.37 万个不同名 |

探针：`scripts/probe-dc-reverse-edges.mjs`。
⇒ **反向查找（"谁 import 我 / 谁提到我"）用文本层就够，便宜 500–1000 倍。**

### 9.3 三条路径（按代价/收益排序）

| 路径 | 做法 | 代价 | 何时用 |
|---|---|---|---|
| **A. 反向边靠"增量累积"（已在做）** | 只建出边（自发现、免费）；**索引区域一扩大，别人的出边就变成我的入边** | 0（顺带） | 现在 |
| **B. 有界文本反查（推荐，S2）** | 要"谁引用我"时，在**候选文件集合**里做 import/标识符正则反查 → 得**候选引用方**，再只解析这些候选确认 | ②③ 的量级 | 局部双向摊开 |
| **C. 预建全局反向索引（后台）** | 全量解析一次 → `edges`/`unresolved_refs`（已有）+ **新增"提及表"** ⇒ 入边查询 O(1) | 一次性全量（12s/296 文件），可后台 | 全局类查询 |

### 9.4 ★ 架构结论：**两级索引**（粗文本层 + 细 AST 层）

不要试图让 AST 一次给出双向全图，而是**分工**：

```
粗层（文本/正则，~0.2ms/文件）        细层（AST，~26ms/文件，只对候选）
  ├─ 谁 import 了路径 X（6ms/全仓）      ├─ 这个符号是什么/签名/类型
  ├─ 谁提及了名字 Y（47ms/全仓）        ├─ 这条是调用还是同名变量（语义确认）
  └─ 反向候选集（宽而便宜）             └─ 精确边（窄而贵）
```

**流程**：粗层给候选（宽）→ 只对候选跑细层（窄）⇒ 双向摊开代价 ≈ 文本扫描 + 少量 AST。
这与真实代码智能系统的分工一致（trigram/zoekt 粗筛，SCIP/LSP 精确），
而且**本项目已有粗层雏形**：FTS5(trigram) 索引 —— 今天它只装在**符号**上，
把来源从 "nodes" 扩展到"**原始标识符 + import 路径**"即可得到 §9.3 的 B/C。

### 9.5 精度纪律（别把粗层当结论）

提及表是**候选集**、不是事实：`foo(` 可能是调用、可能是同名局部变量、可能在注释/字符串里。
- 粗层只用于"缩范围"，**结论必须由细层确认**；
- 对外必须标注 `candidates` vs `confirmed`，**不允许把候选当命中的引用**；
- 反查命中的文件若**未被索引**，按 §4 纪律要么扩块确认、要么标 `partial`。
